# Operations Guide

## Startup order

1. Database is healthy.
2. Migrations run.
3. Web/API starts.
4. Bot starts.
5. Worker starts.

Each process handles SIGTERM and closes its own network/database resources.

## Health endpoints

- `GET /health/live`: process liveness
- `GET /health/ready`: database readiness

## Logs

Set `LOG_JSON=true` in production for machine-readable logs. Correlation/request IDs are generated by FastAPI middleware and included in structured records.

## Scaling

The web service can be scaled horizontally because sessions and state are persisted centrally. Run one scheduler/worker owner per logical outbox stream unless the deployment uses a database with row-locking/claim semantics suitable for multiple workers.

Do not scale a polling Telegram bot horizontally with the same bot token unless the update strategy is intentionally redesigned around a single update consumer.

## Backups

Back up the production database using the database vendor's standard mechanisms. The application does not send raw database backups through Telegram.

## Worker delivery semantics

Scheduled work and outbox delivery use a claim/process/complete lifecycle. Treat delivery as **at-least-once**: an external Telegram call can succeed while the database transaction that marks the record complete fails. Operations that must be idempotent should use stable job/content identifiers and tolerate a duplicate attempt.
